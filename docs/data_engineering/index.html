1. Introduction

The mobile positioning data, acquired from Pickwell, contains columns outside device ID, location and timestamp. The main goal of the preprocessing is to normalize and restructure the raw data.

We intend to use Infostop for stop detection, which requires the data to be sorted by device ID and timestamp. However the raw data is stored daily.

2. Cleaning

The main content of mobile positioning data sets is the device ID, the location and the timestamp.

2.1. Drop insignificant columns

To normalize the data, the less significant columns are dropped, including horizontal_accuracy, altitude, altitude_accuracy, ip, model, carrier, OS, OS_version, manufacturer, and location_method.

OS and OS version will be processed as a device-based supplementary table. On demand, the rest of the columns as well.

2.2. Set timezone

The timestamp looks like a unix epoch, which is the number of seconds that have elapsed since 00:00:00 UTC on January 1, 1970. So, the timezone is set to Europe/Budapest.

2.3. Replace device IDs

The hashed device IDs are 32-character long strings. As it is faster to compare integers than strings, I replaced the string IDs to integer ones. This also saves storage. Considering ASCII represented CSVs, the longest ID it 7 character (as there 1652460 unique devices in the data), which saves 25 bytes as the worst case scenario. Given that the data contains 2860417726 records, the ID replacement could save about 66GB of storage, storing uncompressed.

2.4. Clean OS version

Cleaning the OS version is for calculating the phone’s age. It is possible to associate OS release date for devices whose the OS and the OS version are known. The release dates are collected in YAML format in data/os_version.yaml, collected manually from a Wikipedia pages Android version history, and iOS version history.

As advertisement ID do not survive factory resets or phone changes, it is safe to assume that each device has exactly one OS version. The data confirms this. So, the last day of the activity and the OS version information is gathered for each device. Then, the phone’s relative age is calculated subtracting the release date from the last active day, as in [1]. The relative age is expressed in days, and Table 2 shows some sample lines. Device 8 is using an almost 11-year old Android phone, while device 32 is using an almost 5-year old iPhone.

Note that, OS can be updated on some devices. Some manufacturers like Apple and Google offer multiple years of updates, lower-end devices usually has very limited upgradability. In other words, the relative age is a lower limit, the devices could be even older if the OS was updated.

3.1. Repartition by date

The reason behind partitioning the data by device IDs was to speed up the data processing, but very often the stops are required from a period but for all devices. Thus, the stops are repartitioned by year-month.

4. Calculate speed between pings

The speed between two pings are calculated considering uniform rectilinear motion, using the \$v=d/t\$ equation, where d is the distance between two pings in meters and t is the time difference in seconds. For the spatial distance, the computation uses Haversine distance [1] between locations. The velocity is expressed in m/s.

Speed between pings could be used for inferring the mode of transport. Walking speed typically falls between 1.10 meters per second (4.0 km/h) and 1.65 meters per second (5.9 km/h) [2].

The partitioning step (Section 3) already ordered each partition by device ID and timestamp. The distance computation implemented as a window-style operation, and the distance is calculated between the current and the previous rows. Table 4 shows a sample output. Three columns were added to the data in this step: i) distance_m: great-circle distance in meters, ii) time_diff time difference in seconds, and iii) speed_mps, the velocity in meters per second. The ping tables enriched by these values are saved as different parquet files, within the partitioned/with_speed folder.

Important
 Note that for the first record of a given device there is no difference. Furthermore, the speed is calculated as a simple division with checking the input values.

In other words, the difference and the speed calculation does not consider dates. When a device have sparse appearances the time difference can be as large as days, the spatial distance kilometers making the speed meaningless. Filtering might be required when working with the speed values.

7.3. Altitude

I just want to share a little thought regarding the possibility of using altitude in stop detection — we discussed about this with Riccardo Di Clemente (so shared thoughts). GPS calculates positioning based on the geometry of the satellites up in the sky. As such, we get a highly accurate horizontal position given your device is properly surrounded — that’s not fully true for altitude. Think of it this way: the intersection of range spheres from satellites that are all above you produces a much tighter constraint horizontally than vertically. The "cone" of uncertainty from the satellite geometry is elongated along the vertical axis. Because of this lopsided geometry, the Vertical Dilution of Precision (VDOP) is inherently weaker than the horizontal geometry. As a rule of physics, GPS altitude is typically 1.5 to 3 times less accurate than latitude and longitude (HDOP). In practical numbers, if you have an horizontal accuracy about 5-10 meters → 15-30 m vertical accuracy (that’s a building height). Whatever stop detection algorithms you are using, they will look for a high density of GPS points within a tight radius (a sphere, in the case with altitude) over a specific amount of time. Because vertical GPS data is so noisy, an object sitting perfectly still on a desk might register altitude fluctuations.

— Antonio Desiderio

Home is a hexagon, where an individual has the most stop in the home intervals, work hexagon is analogously where someone has to most stops during work-hours.

10.4. Datetime filtering

Primarily to match the visitation networks to the telecom dataset, datetime filters were introduced, illustrated by Figure 12. The visitations can be filtered by day of week (A-B, C shows no filter), hour (D-F), and even date range. For example, Figure 12/A shows that only weekdays are considered, Figure 12/E shows that only the first six hours of the weekends are considered. Note that Figure 12 shows six-hour blocks to match the telecom data, but the intervals can be selected by hour, so 13-16 or 20-21 hour intervals are also valid options.

Figure 12. Illustration of datetime filtering by day of week (A-C) and hour (D-F).

The Configuration for the visitation network shows the configuration for the night hours of weekdays (Figure 12/D). Besides datetime, the minimum number of stops for home and work locations can be set. By default these are symmetrically 3, which means only those devices are considered for the visitation network building that had home and work location detection from at least 3 stops both locations.

Other elements mentioned in Section 10.3 can be defined like the stop detection variant and the home detection algorithm.

11. dynamic commuting

Due to the sparseness of the data inferring the home and work locations for short periods does not give usable results. So, instead the work and home locations are inferred for th whole data period, and then the movements between the detected home and work locations are calculated daily.

The daily movements are calculated based on the daily appearances in the home and work hexagons. Based on Table 19, let’s consider a device that has a stop at the home hexagon on 1st October and two stops at the work hexagons. As this means that the device traveled between the home and work hexagons, it commuted to work. On 2nd October, device number 1 has no detected stop in the home hexagon, but has a stop in the work hexagons. This case could be interpreted as the commuting also happened.

Table 20 conceptualizes with Bool algebra when commuting should be counted with a more relaxed and a stricter interpretation. Considering fact whether the device had at least one stop in the home and work hexagons. The relaxed commuting cares only about stops in the work hexagon, considering that the device spends the night at home no matter what. The strict interpretation required a stop in the home and in the work hexagon as well on the same day. The relaxed interpretation only considers the work hexagon, and the strict interpretation is the logical and operation.

12. Data catalogue

Parquet format is used for data engineering level (massive data processing), and CSV for analyzation level (e.g., calculated indicators that people would use in a regression).

The output directory should be configured in the main config file, notebooks rely on it. In this document, it is referenced as <OUTPUT>, denoting variables by <> signs.

  • <OUTPUT>/partitioned/<00-ff>/pings.parquet

    • the subdirectory inside partitioned is a hexadecimal value betwee 0 and 255 (00-ff, lowercase), referring the partition (see Section 3)

    • a pings.parquet is about 200 MB

  • <OUTPUT>/id_lookup/id_lookup.json

    • a dictionary to translate the raw hashed device IDs to numbers

  • <OUTPUT>/id_lookup/partition.json

    • a dictionary to translate the numbered IDs to partitions

    • NB: as JSON keys must be strings, the IDs stored as strings.

  • <OUTPUT>/stops/<VARIANT>/<00-ff>.parquet

    • output tables of the Infostop by partition

    • stop detection can be applied using multiple configurations distinguished by a VARIANT label. The VARIANT can be an empty string (""), in which case the output is placed into <OUTPUT>/stops/ folder directly (e.g., <OUTPUT>/stops/00.parquet). If VARIANT is not empty, a subfolder will be created (e.g., <OUTPUT>/stops/much_better_config/00.parquet).

    • the stop detection config file (stop_detection_config.yaml) is copied into the folder to archive the configuration which was used to apply the stop detection.

  • <OUTPUT>/homes/<VARIANT>/home_work_h3_<RESOLUTION>.parquet

    • the "homes" folder contains the home detection results by H3 resolution, between 7 and 10

    • the home detection config file (home_detection_config.yaml) is copied into the folder to archive the configuration which was used to apply the stop detection.

    • VARIANT is the stop detection variant

  • <OUTPUT>/hexagon_network/<VARIANT>/<RESOLUTION>/partials/connections_<00-ff>.parquet

    • VARIANT is the stop detection variant

    • the connections describes a network considering the hexagons as nodes and consecutive stops (by device and day) as edges, which is comparable to the network used in [5].

    • for computational reasons this is stored by partition

  • <OUTPUT>/hexagon_network/<VARIANT>/<RESOLUTION>/edges_[trip|device].csv

    • VARIANT is the stop detection variant

    • as opposed to connections_<PARTITION>, which contains connections by device and day, edges remove this level, and aggregates solely to hexagons.

    • there are two ways to aggregate the network: i) by trips (edges.csv), and ii) by device (edges_unique_device.csv), described in Section 10.1

  • <OUTPUT>/visitation_network/<HOME_DETECTION>/<VARIANT>/<AGGREGATION>/<RES>/.[csv|parquet]

    • commuting-aware, one-hop visitation network

    • HOME_DETECTION is either frequency or howde

    • VARIANT is the stop detection variant

    • AGGREGATION is either trip or device

  • <OUTPUT>/monthly_partitioned_stops/<VARIANT>/<YEAR>-<MONTH>.parquet
